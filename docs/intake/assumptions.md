# Assumptions and unverified facts

Each entry says what is assumed, where it came from, and how it will be checked. Update the status when verified.

| # | Assumption | Source | Status |
|---|---|---|---|
| 1 | Starting Cyrus from inside a Claude Code session breaks it because inherited `CLAUDECODE*` env vars leak into the runner. | Community reports (PLAN.md §6.5) | Unverified in source. Mitigation regardless: Cyrus only ever runs under systemd as user `cyrus`. |
| 2 | Tests must run with a clean environment; a host `GEMINI_API_KEY` changes the default runner. | `RunnerSelectionService.ts:32-35`, baseline run | Verified (see `baseline.md`). |
| 3 | Linux sandbox prerequisites are exactly `socat`, `bwrap`, and a working `bwrap --unshare-user --unshare-pid --unshare-net` probe; AppArmor profile only where AppArmor is enabled. | `packages/claude-runner/src/sandbox-requirements.ts` at `632128f3` | Verified by reading the source. Probe re-run as user `cyrus` in Phase 1. |
| 4 | Instabox public port URLs wake a paused box and reach `127.0.0.1:<port>`. | Instabox `MACHINE.md` / skill docs | Partly false. While the box runs, the URL reaches `127.0.0.1:3456` (HTTP 200 from the placeholder, ~0.9 s from the laptop). A paused box is **not** woken: it returns 503 "Sandbox offline" until the owner runs `instabox resume`. See PLAN.md §13 A6. |
| 5 | A paused box wakes and answers its first request well inside AgentMail's 5-minute Svix timestamp tolerance, so legitimate deliveries are not rejected as stale. | Phase 0 review security note | Moot on Instabox: a paused box never wakes from a webhook, so there is no wake latency to compare with the 5-minute Svix window. Deliveries made while paused fail. Email is recovered by the catch-up job (3d); Telegram/Linear depend on their own retries. The box must be resumed before E2E runs. |
| 6 | The bwrap probe passes as `cyrus` on any host. | Phase 1 on Instabox | False on hosts that overmount files in `/proc` (Instabox `boot_id`). Passes when started via `/usr/local/libexec/cyrus-run`; Cyrus must always start through it (PLAN.md §13 A6). |
| 7 | Cyrus can run without binding `0.0.0.0` (PLAN.md §6, A8 bind-address decision). | Phase 2 on Instabox | Deviation accepted: `CYRUS_HOST_EXTERNAL=true` makes Cyrus bind `0.0.0.0:3456`. Instabox has no inbound ports besides the published URL, and 3456 stays unpublished outside test windows. A bind-host override is a possible later fork change. |
| 8 | Webhook IP validation affects Linear webhooks, and `request.ip` seen by Cyrus identifies the sender. | Phase 2 journal, 2026-10-20 | `WEBHOOK_IP_VALIDATION` is not set in `cyrus.env` (count 0). The journal shows "Webhook IP validation enabled" at every start and "Refreshed GitHub webhook allowlist: 9 CIDRs", so it is on by default and only the GitHub allowlist is loaded. Cyrus does not log `request.ip` for Linear webhooks; Linear deliveries are authenticated by `LINEAR_WEBHOOK_SECRET` signature, not by IP. Behind the Instabox proxy the source IP is the proxy, so IP checks would not be meaningful anyway. |
| 9 | A Linear app (the intake gateway's) can delegate an issue to the Cyrus app user and start a session. | Phase 2, CYR-6 | Verified: app-to-app delegation works (PLAN.md §8 A8, delegate path). |
| 10 | Instabox secrets reach the box unquoted. | Phase 2 | False: `/run/instabox/secrets/env` has lines `export NAME='VALUE'` with single quotes. `secrets-bridge` strips that one matching layer, then validates the value against `[A-Za-z0-9._:/+=-]`. |
| 11 | `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` leaves other environment variables alone. | Phase 2 | False for `GIT_CONFIG_GLOBAL`: the scrub strips it inside sandboxed sessions. The git identity and credential helper therefore come from `/etc/gitconfig.d` through a system `includeIf`, not from a per-process variable. |
| 12 | Docker/containerd can stay installed on Instabox. | Phase 2 | False: container runtime sockets (`/run/docker.sock`) break the env scrub's sandboxing of commands. Docker is disabled on Instabox (`DISABLE_CONTAINER_RUNTIME=yes`); a stale `/run/docker.sock` file remains, harmless because nothing listens. |
